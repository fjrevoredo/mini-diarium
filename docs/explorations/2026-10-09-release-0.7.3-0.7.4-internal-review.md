# Internal Review: Releases 0.7.3 and 0.7.4

**Date:** 2026-10-09
**Scope:** `git diff v0.7.2..v0.7.4` (0.7.3 = `v0.7.2..v0.7.3`, 0.7.4 = `v0.7.3..v0.7.4`). 49 commits, 279 files.
**Reviewers:** Claude (lead, backend, architecture, security) paired with an OpenCode agent (frontend, tests, scripts, CI). Each side challenged the other's findings against the code before they entered this report.
**Mode:** Read-only. No source file changed, nothing committed.

## Summary

The two releases are in good shape where it matters most. No finding breaks encryption, leaks plaintext to disk, or adds a network path. The new subsystems (file attachments, the forward-compatibility guard, the tag-aware Timeline) follow the documented security model, and their tests assert real behavior.

The issues cluster in three classes that the current best-practice docs do not yet name:

1. **Composition without atomicity.** Core write functions each own a `BEGIN IMMEDIATE`, so they cannot nest. Multi-step operations built from them (per-entry backup restore) can stop halfway.
2. **Async completion races in frontend state.** Several awaited calls write shared signals without re-checking that the session, entry, or filter is still the one that started the call.
3. **Gates that report green while the thing they guard is broken.** The Nix build has failed on every master push in range, but the workflow exits 0. A new test suite exists that no gate runs.

One P1 needs action now (Nix). Eight P2 findings are worth scheduling. Four P3 items are hygiene.

## P1

### R-01 Nix build broken on master, CI reports success

**Where:** `nix/package.nix:61`, `.github/workflows/nix.yml:38-58`

`package-lock.json` changed in both releases (Vitest 4.1.10 to 5.0.1, among others), but `npmDepsHash` is the same value in `v0.7.2`, `v0.7.3`, and `v0.7.4`. Root `CLAUDE.md` ("Updating Dependencies") requires refreshing it with every lockfile change.

The workflow was meant to self-heal: on a push build failure it rewrites the hash and pushes a commit. That push is rejected by branch protection, and the script then reaches `exit 0`. Evidence from run `37855720300` (master, "Pre-release checks", 2026-10-08):

```
error: hash mismatch in fixed-output derivation '...mini-diarium-frontend-0.7.4-npm-deps.drv':
   specified: sha256-j/R5j1QAbXiuz9yFB8YuaOL2LR+q+Gf5NXRioL1q5pE=
   got:       sha256-4PLAHcSfvWctc3pYS4muzG1S5tFwh9Z6QHJpRfDLk10=
remote: error: GH013: Repository rule violations found for refs/heads/master.
 ! [remote rejected] master -> master (push declined due to repository rule violations)
```

The run is listed as `success`. Dependabot PR runs fail, which makes the red look like PR noise. The Nix package has not built since at least 0.7.3.

**Rule broken:** root `CLAUDE.md` dependency checklist; `CI_BEST_PRACTICES.md` (a gate must not pass when its check fails).

**Recommendation:**
1. Set `npmDepsHash` to the `got:` value above (re-check against current master first).
2. Make the workflow fail when the auto-fix cannot land. Either drop the auto-commit and print the new hash in the failure message, or open a PR instead of pushing to master. Never `exit 0` after an unverified `git push`.
3. Add the hash refresh to the `sync-lockfiles` skill so the manual path covers it.

**Validation:** tagged files compared directly; CI log read with `gh run view`. Nix is not installed locally, so no local build was attempted.

## P2

### R-02 Per-entry backup restore can leave a partially restored entry

**Where:** `crates/mini-diarium-core/src/backup/restore_entries.rs:150-187, 205-221`; `db/queries/entries/insert.rs:52-84`; `db/queries/attachments/storage.rs:73-133`

Restoring one entry from a snapshot runs these steps, each with its own commit: copy attachment blobs (autocommit), `insert_entry_with_images` (own transaction), link each attachment (autocommit), add tags. On failure the code calls `let _ = cleanup_orphaned_attachments(...)`, which removes unlinked blobs but not the inserted entry, its earlier links, or the rewritten HTML.

The partner reproduced three outcomes against the real core crate. The link failures were injected with SQLite triggers. The corrupt blob was made by overwriting its ciphertext:

| Fault | Live journal after the error |
|-------|------------------------------|
| Second attachment link fails | New entry kept with 1 of 2 links. Its HTML still holds `data-attachment-ref="2"`, which no longer resolves. |
| Second snapshot blob is corrupt | No entry, but the first copied blob stays unlinked (`copy_attachment_blobs(...)?` returns before cleanup). |
| Tag link fails | New entry and both files kept, without its tag. |

The snapshot and existing live entries stayed intact in all three. `restore_entries.rs:133-136` documents that earlier entries of a batch may stay after an error. That is acceptable. One entry being half-restored is not.

**Rule broken:** restore does report the error, so nothing is swallowed. The gap is per-entry atomicity, which the restore module's goal of a faithful copy depends on. Restore is the recovery path, so a partial result there costs more than elsewhere.

**Recommendation:** make "copy blobs, insert entry, link files, link tags" one atomic unit per entry. Wrapping today's functions in an outer `BEGIN` or `SAVEPOINT` does not work: their inner `BEGIN IMMEDIATE` fails, and their error path issues an unconditional `ROLLBACK` that would abort the caller's transaction. Change the contract first (see R-11): transaction-free inner primitives, with the transaction owned by the outermost operation, or savepoints throughout.

### R-03 Async replies overwrite newer frontend state

Three instances of one pattern: an awaited reply writes a shared signal without checking that the context which started it is still current.

**a. Attachment mutations across a session reset.** `src/components/editor/EntryAttachments.tsx:131-135, 165-168`. `handleAdd` checks `sessionMark()` before `await addEntryAttachment(...)` but not after. `upsertEntryAttachment` only compares `attachmentsEntryId()`, and entry ids repeat across journals. A reply that lands after a lock, journal switch, or restore can insert a stale file name into the new session's list. In the partner's test the new journal's chip was renamed to `old-private-report.pdf`. Display only, no bytes cross, but it is a cross-journal metadata bleed.

**b. List load overlapping a mutation.** `src/state/entryAttachments.ts:23-33`. A load started before a successful add can resolve after it and replace the list with its older, empty result. `attachmentsLoaded` becomes true, so the entry reads as attachment-free in the UI. The backend refuses to auto-delete it, so no data is lost.

**c. Clearing a pending tag filter.** `src/state/tags.ts:24-33, 52-55`. `setTagFilter` writes `tagFilteredDates` unconditionally after its await, and `clearTagFilter` does not invalidate it. If the user clears the filter while the lookup is pending, the filtered dates come back with no active filter. The Timeline shows no banner, but the new Ctrl+[ / Ctrl+] navigation (`src/lib/day-navigation.ts:27-28`) still uses the hidden filtered list and skips real entry days. `refreshTagFilter` in the same file has a limited guard: it compares the tag id, which does not cover a session reset or an older request for the same tag.

**Rule broken:** `FRONTEND_BEST_PRACTICES.md` "Put State In The Smallest Correct Owner"; `src/CLAUDE.md` State Management invariant that session state stays cleared after reset.

**Recommendation:** one rule, applied everywhere: after every `await`, re-check the token captured before it (session mark, load revision, filter token) before writing state or setting an error. Give `entryAttachments.ts` a revision counter shared by loads and mutations. Give `setTagFilter` a token that `clearTagFilter` bumps. Add this rule to `FRONTEND_BEST_PRACTICES.md`, since TODO-0089 (editor) was the same class.

**Validation:** focused Vitest tests with deferred promises against the real components and state modules reproduced each case. Native IPC timing was not tested.

### R-04 Heavy attachment work runs inline on the native event thread, under the journal mutex

**Where:** `src-tauri/src/commands/attachments.rs:152-174`; all commands are synchronous `pub fn`

`add_entry_attachment_inner` reads the source file (up to 20 MB), fingerprints it, encrypts it, and stores it, all inside `with_unlocked_db`. The partner traced the installed Tauri 2.12.0 / wry 0.57.0 sources: on Windows a synchronous command runs directly in the WebView2 custom-protocol callback, with no worker pool. A MockRuntime test of the unchanged tagged helper with a 20 MB file ran on the caller's thread and took 3.5 s in a debug build. That number is not a release measurement, but it shows the shape: the window and every other command wait.

The plugin-based Markdown export (the path `ExportOverlay` uses) releases the DB lock while it formats and writes. Only its per-attachment decrypt re-takes the lock, so the mutex part of this finding is limited to attach. The direct `export_markdown` command does hold the lock through asset writes, but the UI does not call it.

**Rule broken:** `RUST_BEST_PRACTICES.md` "Keep Lock Scope Small And Obvious" (clone out of state before file I/O). `save_attachment_copy_inner` in the same file already does it right: decrypt under the lock, write after.

**Recommendation:** read and validate the source file before taking the DB lock, then re-check that the same journal is still open before committing. Move attach, export, and restore to `async` commands that do their heavy work in `spawn_blocking`. Measure a release build with a 20 MB file before and after.

### R-05 Entry-protection and soft-delete policy is not owned by core

**Where:** `src-tauri/src/commands/entries.rs:57, 211-240, 262`; `commands/tags.rs:33, 57`; `commands/attachments.rs:21-27`; core `recalculate.rs:32-36`

The per-entry lock check (`db::is_entry_locked` plus the literal `"entry is locked"`) is copied five times in the app crate. 0.7.4 added the fifth. Core write functions (`add_attachment_to_entry`, `update_entry`, `add_tag_to_entry`, `delete_entry_by_id`) do not check it. Core's own `recalculate_all_word_counts` does, so the layering is inconsistent. The "is this entry empty" rule (blank title and body, and no attachments) is also composed in two app-crate places.

The duplication already let one path slip. `delete_entry_if_empty_inner` (`entries.rs:211-240`) checks neither the lock flag nor `is_entry_locked`. A test of the tagged helper deleted a locked, blank, attachment-free entry. This predates the range, but 0.7.4 edited this helper to add the attachment check and left the lock gap.

Entry lock is protection against accidental edits, not a security boundary, so this is P2 drift rather than a security issue. It does matter for the open-core plan: a second consumer of the core façade gets none of these rules.

**Recommendation:** move `ensure_entry_unlocked` and an `entry_is_empty` predicate into core, with one exported constant for the error string. Have the core write operations enforce the lock. Keep hard delete and blank-entry cleanup as separate APIs: hard delete must not become blank-only. Add a regression test for the locked blank entry.

**Rule broken:** `RUST_BEST_PRACTICES.md` "Centralize Repeated Security-Sensitive Logic" ("consider a helper before adding a third"); `docs/OPEN_CORE_STRATEGY.md`.

### R-06 Journal registration silently changes the filename the user picked

**Where:** `src-tauri/src/commands/auth/auth_journals.rs:122-126`; `crates/mini-diarium-core/src/config.rs:197-220`; `src/components/auth/JournalPicker.tsx:140-215`

TODO-0112 switched journal creation to a native save dialog. The picker validates the exact path the dialog returns, then `add_journal` passes the filename through `journal_dir_name`, a folder-name sanitizer that collapses whitespace runs, strips `:`, and truncates to 64 characters. The code comment says this is a no-op for native dialogs. It is not:

| Picked | Registered |
|--------|-----------|
| 65 letters + `.db` | 64 letters, no extension |
| `work  notes.db` | `work notes.db` |
| `work:notes.db` (legal on Linux) | `worknotes.db` |

With "Open existing", the picker confirms the selected database exists, then registers a different, absent path. The user is then led into creating a new empty journal under the name they believe is theirs. The original file is untouched, so this is confusion rather than loss. Create cannot overwrite, because `create_diary` refuses an existing path.

**Rule broken:** `FRONTEND_BEST_PRACTICES.md` "Keep Sensitive UI Flows Ordered And Testable" (one target identity from check to action).

**Recommendation:** validate the filename and reject bad input with a clear error. Never rewrite a filename. Apply any Flatpak free-text normalization in the form, before the existence check, so the checked path and the registered path are the same string.

**Validation:** the tagged `journal_dir_name` was compiled and run on the three inputs above.

### R-07 JSON, the structural export path, cannot carry attachment contents

**Where:** `crates/mini-diarium-core/src/export/json.rs:42-56`; `src-tauri/src/commands/import.rs:44-48`; `website/docs-src/05-export.md:46-48`

JSON export lists `{ name, mime_type, byte_size }` only, and JSON import strips attachment refs. Images round-trip through JSON as data URIs. Attachments do not. Rhai exporters see nothing (tracked as TODO-0117). Markdown-with-assets and backups do carry the bytes, so migration is possible. The docs state the limits accurately.

PHILOSOPHY.md calls JSON "the structural export path". The export leaves the originals untouched. A user who keeps that JSON as the only copy of the journal has no attachment contents, and the UI does not warn about it.

**Recommendation:** record a decision (ADR) on how attachments travel in structural exports: base64 inside the JSON, or a sibling folder with a manifest. Until then, show a warning in the export dialog when the selection includes attachments and the format cannot carry them. Keep the import-side ref stripping until a real attachment import contract exists.

### R-08 New website-generator tests are not run by any gate

**Where:** `scripts/website-generator-utils.test.mjs`; `vitest.config.ts:16` (`'scripts/**'` excluded)

The suite (9 tests, `node:test`) passes when run by hand with `node --test`. No package script, workflow, or `bun run pre-commit` step invokes it, and Vitest excludes `scripts/**`. A regression in the image-header checks cannot fail CI.

**Recommendation:** add `test:scripts` (`node --test scripts/*.test.mjs`) and call it from CI and the pre-commit gate. Consider a guard that fails when a `*.test.*` file sits outside every runner's include list.

### R-09 Inline attachment references are buttons a keyboard cannot reach

**Where:** `src/components/editor/extensions/AttachmentRef.ts:105-127`

The NodeView sets `role="button"` and handles only `click`. It has no `tabindex` and no Enter or Space handler. Tested with a real TipTap editor: `tabIndex === -1`, click saves, Enter and Space do nothing. The chip strip gives keyboard users another way to save the file, but the inline control announces itself as a button and does not act as one.

**Recommendation:** make it focusable with Enter and Space activation. Stop those keys from reaching the editor and the global shortcut handler. Keep save-a-copy working on a locked entry.

## P3

### R-10 Save-a-copy guard compares path spelling, not file identity

**Where:** `src-tauri/src/commands/attachments.rs:84-133, 230`

`ensure_safe_destination` canonicalizes the parent folder and compares names. It does not check whether an existing destination file is the same file as `config.json`, the journal, or its side files. `std::fs::write` then truncates through hard links. The partner confirmed on Windows: a hard link `copy.json` pointing at `config.json` passed the guard, and the attachment bytes replaced `config.json`. For a local-only journal that destroys the device key. The SQLite-header check still protects any alias of a healthy database.

This needs a pre-existing hard link, so the realistic risk is low. It is P3 because the guard exists to stop exactly this class of accident.

**Recommendation:** for an existing destination, compare file identity (volume and file index on Windows, device and inode on Unix) with the protected files before writing. Do not switch to a write-to-temp-then-rename scheme without care: a temporary file is extra plaintext on disk, which `save_attachment_copy` promises to avoid (`attachments.rs:234-235`).

### R-11 Transaction boilerplate copied six times next to an existing helper

**Where:** `db/queries/attachments/storage.rs:47-67` (new `in_transaction`), `entries/recalculate.rs:22-58` (new), `entries/delete.rs`, `entries/insert.rs`, `entries/update.rs`; existing `db/schema/migrations/mod.rs:51` `run_migration_transaction`

Both releases added copies of the BEGIN, COMMIT, ROLLBACK closure although an identical helper already exists. This is the root cause of R-02: no function in this style can be called inside another's transaction.

**Recommendation:** fix together with R-02. One core helper that owns the transaction, with inner primitives that never begin one. rusqlite's `Transaction` and `Savepoint` types also give rollback on drop, including on panic, which the hand-written closures do not.

### R-12 PHILOSOPHY.md Part II facts are stale

`PHILOSOPHY.md:264` says schema v13 (it is v14). `:198-201` shows an `ExportPlugin` signature with neither the tags and attachments parameters nor the `ExportOutput` return type. `:278` says "8 signal modules" (there are 17 non-test files in `src/state/`). Reviewers use this file as a yardstick, so wrong facts there mislead future reviews.

Attachments do not violate the "no media galleries" non-goal: there is no viewer, only save-a-copy (an in-app viewer is TODO-0119). The feature still deserves a short scope note under the Decision Framework, since it widens the stored data types.

**Recommendation:** fix the facts and replace counts and signatures with pointers to the source. Add an attachments scope note or ADR covering why the feature is in core, the 20 MB cap, and the save-a-copy-only stance.

### R-13 String-matched IPC error contract and wide attachment API surface

**Errors.** 0.7.4 added nine regexes to `src/lib/errors.ts`. No test ties the Rust strings (some are named constants, such as `JOURNAL_TOO_NEW` in `compat.rs`) to those regexes, so a reworded backend message silently falls back. Three new validation strings (`Attachment name contains control characters`, `... is too long`, `Attachment file name is not valid`) have no mapping. They reach the UI in untranslated English. They hold no path or user data.

**API surface.** `upsert_attachment_blob`, `link_attachment`, `cleanup_orphaned_attachments`, and `mime_for_extension` are documented in `API.md` and exported from the façade, but nothing outside core uses them. This does not breach the M2 rule, since they are documented. The first two are non-atomic building blocks that skip the entry lock, so `pub(crate)` is the safer default.

**Recommendation:** for new commands, return structured errors (`{ code, message }`) or generate a shared list with a cross-language test. Narrow the four helpers to `pub(crate)` when R-02 and R-05 are done.

## Done well

- **Forward-compatibility guard (TODO-0122).** Every open path calls the guard right after opening and before any write or KDF, so a refused file stays byte-identical. Restore checks the staged copy before the safety snapshot. A tripwire test fails on every schema bump until the marker decision is recorded. This is a strong model for future cross-version rules.
- **Attachment storage boundary.** Bytes never cross IPC. Reads are scoped to the owning entry by a join, so knowing an attachment id is not enough to read it. Source reads are bounded (`take(cap + 1)`), buffers are `Zeroizing`, and the plaintext metadata (`mime_type`, `byte_size`) is disclosed honestly in the user docs. The 0.7.4 hardening commit closed real holes: protected save destinations, a session guard for plugin export, and stripping foreign refs on import.
- **Schema v14 safety for older apps.** `ON DELETE RESTRICT` on `entry_attachments.entry_id` means a pre-0.7.4 app that thinks an attachment-only entry is empty fails to delete it instead of dropping its files.
- **Escape ownership.** `MainLayout` records overlay state in a capture-phase listener before dialogs close, and the test pins the real event-order problem rather than a later signal value.
- **Timeline tag filter.** Filters per entry, not per date, with no nested buttons. Tests cover tagged and untagged siblings on the same day.
- **Clean gates.** Clippy, both test suites, lint, type-check, locales, and the façade greps are all clean.

## Proposed best-practice additions

The three classes in the summary are not yet written down as rules. These one-line additions would catch the next instance in review:

- `FRONTEND_BEST_PRACTICES.md`: "After every `await`, re-check the token captured before it (session, entry, revision, filter) before writing shared state."
- `RUST_BEST_PRACTICES.md`: "Core write primitives do not open transactions. The outermost operation owns the transaction, so multi-step operations stay atomic."
- `CI_BEST_PRACTICES.md`: "An auto-fix step must fail the job when its fix cannot land. Never `exit 0` after an unchecked push." and "Every test file must belong to a runner that a gate executes."

## Method and limits

- The lead reviewed the Rust workspace, IPC, schema, and docs. The partner reviewed `src/`, `scripts/`, `.github/`, and lockfiles. Each side then tried to falsify the other's findings. Six of the lead's seven findings were adjusted or narrowed in that round. One (façade over-exposure) was downgraded from a rule breach to an API-design note. The partner added R-10 and the soft-delete lock gap in R-05.
- Validation used focused external harnesses that call the real tagged code (Vitest with deferred promises, a Cargo crate depending on `mini-diarium-core`, the tagged `journal_dir_name` compiled with `rustc`). No production logic was reimplemented to prove a finding. Harness files live outside the repository.
- Not covered: live desktop UI, native IPC timing, release-build performance, macOS and Linux runtime, Flatpak, E2E, and the `website/` content changes.
