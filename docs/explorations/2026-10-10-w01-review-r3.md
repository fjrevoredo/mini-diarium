## Findings

### R3-01 — P3: qualify the transaction error and cleanup contract

**Location:** `crates/mini-diarium-core/API.md:90-99`, especially the new statement at lines 97-99 that the outermost unit "rolls back and returns the same error" after transaction loss or a failed nested rollback.

The helper preserves a closure error at `transaction.rs:85` through `f()?`. Its guard then performs cleanup. The poison check at lines 107-108 runs only if the outer closure returned `Ok`. Thus a poisoned outer unit can return the original closure error, not `ERR_WRITE_UNIT_LOST`. This is correct behavior, but the new API text promises a different error without this condition.

The existing `test_transaction_returns_original_error_after_sqlite_rolled_back_everything` at lines 353-370 already proves original-error preservation after parent loss. A direct Case B example has the same result: the outer closure loses its transaction, catches the refusal from a later helper call, then returns a different closure error. The poison flag is set, but `f()?` returns that different error.

The adjacent guarantee that the connection is "never left in a half-open transaction" also needs an exception. The new guard explicitly handles a failed outer rollback that leaves SQLite outside autocommit mode at lines 148-152. It leaves depth at zero and refuses later helper writes as Case A. This is safe refusal, not guaranteed successful cleanup. SQLite documents transaction loss detection through autocommit [S1, S3] and rollback on connection destruction [S4]. rusqlite can fail while preparing a batch statement, before the rollback opcode runs [SRC1]. The bundled rollback opcode sets autocommit after executing rollback [SRC3]; this does not guarantee that preparation succeeds.

**Required correction:** state that a poisoned unit cannot commit; preserve an existing closure error; return `ERR_WRITE_UNIT_LOST` when an otherwise successful outer closure reaches the poison check. Describe rollback as attempted cleanup, with later writes refused if an outer rollback leaves a transaction open. Keep the implementation's original-error policy.

### R3-02 — P3: remove the contradictory W-07 test status

**Location:** `docs/explorations/2026-10-10-core-write-contract-adversarial-review.md:263-265`.

The updated row at line 265 correctly says that `test_transaction_commit_failure_rolls_back` and `test_transaction_trigger_raise_rollback_loses_whole_unit` cover the preceding two rows. However, the COMMIT row still says "No test drives it", and the real-rollback row still describes only the simulated rollback test. These now read as current gaps and conflict with the new completion statement.

The COMMIT test really creates the requested failure: it selects DELETE journal mode, starts and steps a read on a second connection, disables the writer's busy timeout, and requires a `COMMIT failed:` error. It then checks autocommit, depth zero, and the absence of the row through the separate reader after ending its read transaction (`transaction.rs:470-497`). This matches SQLite's documented busy-COMMIT behavior [S1 §2.3]. The trigger test really invokes SQLite's `RAISE(ROLLBACK, ...)`, rather than issuing a raw rollback (`transaction.rs:420-444`; [S5]).

**Required correction:** mark these two rows as covered, or label their old descriptions as historical. No new test is required to correct this status.

| Case B: positive depth, autocommit | Sets poison and returns `ERR_WRITE_UNIT_LOST` before SQL, depth increment, or closure execution (lines 72-75). Existing guards later remove their levels. An outer `Ok` cannot bypass the poison check. |

The raw-transaction prohibition excludes that behavior; no current caller was found to do it. Likewise, swallowed errors followed by raw write primitives can still commit in autocommit mode. The API correctly retains this caller restriction. Neither limit is a new W-01 regression.

## Test limits and non-blocking notes

1. **The poison-policy test proves the policy, not failed-rollback detection.** `test_transaction_poisoned_unit_rolls_back_instead_of_committing` directly sets `write_poisoned` at line 455. It proves that the outermost unit rolls back instead of committing when poisoned. It does not execute the branch that sets poison after failed nested cleanup.
2. **"A test cannot drive that failure" is too broad** (`transaction.rs:448-449`). A test can remove the nested `md_write` savepoint by a raw RELEASE inside the nested closure, then return an error. The guard's ROLLBACK TO then fails with no matching savepoint, while the outer BEGIN remains open. Catching that error and returning outer `Ok` can test the production poison-setting branch. SQLite explicitly documents that a missing-name ROLLBACK TO fails without changing the database [S2; SRC2]. This is deliberate test-only misuse, not a claim that a current production caller does it. An actual rollback I/O fault is a separate test problem.
3. **Case A could assert more directly that the closure did not run.** The current test checks the exact refusal, an open foreign transaction, and depth zero. It rolls back before checking rows, so that final empty-row check alone would not detect a wrongly executed closure. A closure-call flag and a foreign row checked before cleanup would strengthen it. Code inspection confirms the closure is not called today.
4. **No dedicated SAVEPOINT-creation or RELEASE-failure test is present.** The paths were reviewed in code and installed sources, not exercised during this review. SQLite exposes deterministic failures with active write statements [SRC2]. The reported line coverage does not prove coverage of every error outcome.
5. The success, ordinary-error, nested-error, two-level nesting, and outer/nested unwind tests assert the claimed row results and depth cleanup. The explicit-ROLLBACK tests are correctly labeled simulations. The trigger test supplies the real SQLite rollback case.

These notes do not establish a runtime defect. The two documented uncovered rollback-failure branches remain a test limit, not evidence that their reviewed control flow is wrong.
