# v0.5.3 Branch Code Review

Date: 2026-06-04
Branch: `feature-v0.5.3`
Reviewed commit: `e3b0809`
Comparison target: `master` (`master...HEAD`)

## Part 1: Assessment

This branch adds several valuable v0.5.3 features: named links, per-entry font metadata, a DB-backed encrypted image store, image-aware exports, import/export metadata support, preference/UI additions, and project-agent workflow improvements. The broad shape is consistent with the app's direction: sensitive entry metadata is encrypted, image references are moved out of the main HTML on normal save, command registration is present, and docs/locales were updated.

The main code quality risks are concentrated around the new editor/link and image-store boundaries. Normal editor saves go through the new image extraction path, but imports and some frontend resolver paths do not yet share the same invariant. Link opening sanitizes URLs when the user creates links through the dialog, but not when opening links already present in entry HTML. The image picker also exposes a scalability problem by decrypting every stored image in one IPC call.

Validation note: no further tests were run after the user asked to skip tests. Before that interruption, `type-check` and `validate:locales` passed, `lint` failed on `ImagePickerOverlay.tsx`, and the full backend test suite had known auth/test-fixture failures that the team is already fixing. A later edit added a local ESLint suppression for the image-picker ref, so the current remediation is to replace that suppression with lint-visible Solid ref wiring rather than treating the original lint error as still unaddressed.

## Part 2: Actionable Fixes

### 1. Replace the image-picker ref lint suppression with lint-visible code

Severity: Medium

[src/components/overlays/ImagePickerOverlay.tsx](../src/components/overlays/ImagePickerOverlay.tsx:14) now suppresses `no-unassigned-vars` because `dialogRef` is declared with a definite assignment assertion and assigned through Solid's `ref={dialogRef}` syntax. That suppression is narrow, but it leaves a known lint exception in new feature code where a simple callback ref avoids the issue entirely.

Suggested fix:

Use a callback ref that the linter can see, remove the suppression comment, and guard focus in `onMount`.

```tsx
let dialogRef: HTMLDivElement | undefined;

onMount(() => dialogRef?.focus());

// ...
ref={(el) => {
  dialogRef = el;
}}
```

Validation:

- `cmd.exe /c bun run lint` should pass without an inline suppression for this ref.
- No new behavior test is required solely for the ref rewrite. Keep any existing overlay render test if one is added for the image picker later.

### 2. Sanitize stored/imported links before calling `openUrl`

Severity: High

The link dialog normalizes and rejects unsafe protocols in [src/components/editor/LinkOverlay.tsx](../src/components/editor/LinkOverlay.tsx:45), and the dialog's explicit "Open" button uses that normalized value at line 188. However, editor Ctrl/Cmd-click opens the raw `href` from the rendered anchor in [src/components/editor/extensions/LinkWithDialog.ts](../src/components/editor/extensions/LinkWithDialog.ts:90). That path can be reached by links loaded from imported JSON/HTML or older saved content, bypassing the dialog sanitizer.

Impact:

- A stored link with `file:`, `javascript:`, `data:`, or another unsupported scheme can reach Tauri opener.
- Even if some schemes are blocked by the OS/plugin, the frontend should enforce the app's allowed link policy before crossing the Tauri plugin boundary.

Suggested fix:

Move URL normalization/allow-listing into a shared helper, for example `src/lib/safe-links.ts`, and use it from both `LinkOverlay` and `handleEditorLinkClick`.

```ts
export function normalizeUserLink(input: string): string | null {
  const trimmed = input.trim();
  if (!trimmed) return null;

  const protocolMatch = trimmed.match(/^([a-z][a-z0-9+.-]*):/i);
  if (protocolMatch) {
    const protocol = protocolMatch[1].toLowerCase();
    return ['http', 'https', 'mailto', 'tel'].includes(protocol) ? trimmed : null;
  }

  if (trimmed.includes('@') && !/\s/.test(trimmed)) return `mailto:${trimmed}`;
  if (/^\+?[\d\s().-]+$/.test(trimmed) && /\d/.test(trimmed)) {
    return `tel:${trimmed.replace(/[\s().-]/g, '')}`;
  }
  return `https://${trimmed}`;
}
```

Then in `handleEditorLinkClick`, only call `openUrl(normalized)` when normalization returns a value.

Tests to add:

- `handleEditorLinkClick` should not call `openUrl` for `javascript:alert(1)`, `data:text/html,...`, `file:///...`, or unknown protocols.
- It should still open `https:`, `http:`, `mailto:`, `tel:`, and bare-domain links after normalization if bare-domain links can exist in stored content.

### 3. Normalize imported data-URL images into the image store

Severity: High

Normal editor saves call `update_entry_with_images()` through [src-tauri/src/commands/entries.rs](../src-tauri/src/commands/entries.rs:32), which extracts `data:image/...` URLs, stores encrypted image bytes, rewrites entry HTML to `image-id://...`, and updates `entry_images`. Imports do not use that path. [src-tauri/src/commands/import.rs](../src-tauri/src/commands/import.rs:38) loops through parsed entries and calls `queries::insert_entry(db, &entry)` directly at line 52.

Impact:

- A JSON export resolves stored image IDs back to portable data URLs in [src-tauri/src/commands/export.rs](../src-tauri/src/commands/export.rs:37).
- Re-importing that export preserves the data URLs inside encrypted entry HTML instead of deduplicating them into `images` and `entry_images`.
- The same user-visible image can be stored in two formats depending on whether it came from the editor or from import, increasing storage size and making future image operations harder.

Suggested fix:

Centralize an insert path that applies the same image invariant as save. Options:

- Add `insert_entry_with_images(db, &entry)` that inserts the row inside a transaction, extracts images from `entry.text`, updates the new row's text to `image-id://...`, and writes `entry_images`.
- Or keep `insert_entry()` low-level and make `import_entries()` call `update_entry_with_images()` immediately after insert using `last_insert_rowid()`, inside one transaction for each entry or for the whole import batch.

Keep `insert_entry()` available for tests and internal call sites that intentionally insert raw HTML, but make user-facing import paths use the invariant-preserving helper.

Tests to add:

- Export an entry with a stored image to JSON, import that JSON, then assert the imported row's encrypted HTML decrypts to `image-id://...` and `images`/`entry_images` contain the expected rows.
- Import a legacy Mini Diary JSON entry with `data:image/png;base64,...` and assert it is normalized the same way.
- Import an entry with no images and assert the text remains unchanged.

### 4. Avoid decrypting every journal image for the picker

Severity: Medium

The image picker calls `listJournalImages()` as soon as it opens in [src/components/overlays/ImagePickerOverlay.tsx](../src/components/overlays/ImagePickerOverlay.tsx:13). The backend implementation returns every image in the journal, decrypted and base64 encoded, through [src-tauri/src/db/queries/images.rs](../src-tauri/src/db/queries/images.rs:115).

Impact:

- The DB lock is held while all image rows are read, decrypted, base64 encoded, serialized, and returned over IPC.
- A journal with many or large images can freeze the editor and create a large plaintext image payload in frontend memory.
- This works for small journals but does not scale with the feature's intended use.

Suggested fix:

Split the API into summary and data fetches:

- `list_journal_image_summaries(limit, offset)` returning `id`, `mime_type`, `created_at`, and optionally dimensions/thumbnail metadata.
- `get_image_data(image_id)` returning one decrypted image only when the user inserts/previews it.
- Consider a small encrypted thumbnail column if gallery browsing needs image previews without decrypting full originals.

Tests to add:

- Backend test that summary listing does not return `data_base64`.
- Frontend test that opening the picker calls the summary command and only requests full data for the selected image.

### 5. Enforce image MIME, byte-size, and magic-byte validation at the storage boundary

Severity: Medium

The persistent image store accepts any `data:image/<subtype>;base64,...` that `extract_src_data_uri()` can parse in [src-tauri/src/db/queries/images.rs](../src-tauri/src/db/queries/images.rs:327). `upsert_image()` then stores the provided MIME string and plaintext bytes without checking an allow-list or magic bytes at line 18. The frontend and `read_file_bytes()` extension checks limit common paths, but imports and existing HTML can bypass those UI-level filters.

Impact:

- Unsupported or scriptable image types such as SVG can become persistent journal content.
- Extremely large base64 images can be imported and stored without the same resizing/size limits applied by the editor canvas path.
- The backend currently trusts MIME labels supplied by entry HTML, which is not a durable security boundary.

Suggested fix:

Add a backend validator before `upsert_image()` stores bytes:

- Allow only the same image families the app supports: png, jpeg, gif, webp, bmp.
- Verify magic bytes where practical instead of trusting the MIME string.
- Enforce a max stored image byte size. Match the product expectation, for example 20 MB or a stricter editor-specific limit.
- Reject or leave unsupported images embedded only if there is a clear compatibility reason; otherwise return a controlled import/save error.

Tests to add:

- `data:image/svg+xml` is rejected or left unpersisted according to the chosen behavior.
- A MIME/type mismatch such as `image/png` with JPEG bytes is rejected.
- Oversized image bytes are rejected before encryption/storage.

### 6. Align frontend image reference resolution with backend semantics

Severity: Medium

The backend deliberately treats `image-id://N` as an image reference only when it appears in an `<img src=...>` attribute; see [src-tauri/src/db/queries/images.rs](../src-tauri/src/db/queries/images.rs:181) and `extract_src_image_ref()` at line 269. The frontend helper is broader: [src/lib/image-refs.ts](../src/lib/image-refs.ts:3) treats any `image-id://\d+` in HTML as a signal to fetch images, and line 12 replaces any `image-id://ID` immediately followed by a quote, regardless of whether it is an image `src`.

Impact:

- Display behavior can diverge from persisted-storage behavior.
- A literal text mention like `image-id://1"` can be changed on load if that image is associated with the entry.
- Several call sites duplicate the same resolve-on-load pattern, which makes future fixes easy to miss.

Suggested fix:

Make the frontend resolver parse only `<img src="image-id://N">` and `<img src='image-id://N'>`, matching the backend. Better yet, move resolution behind one backend command such as `get_entry_images_resolved(entry_id)` or return resolved HTML from `get_entries_for_date()` only when requested, so one implementation owns the parsing.

Tests to add:

- Frontend helper does not resolve plain text `image-id://1"` outside an `<img src>`.
- It resolves both single-quoted and double-quoted image `src` attributes.
- A navigation/load test covers the shared helper rather than each call site implementing its own resolution branch.

### 7. Make schema migrations roll back explicitly on failure

Severity: Medium

The new migrations use `execute_batch("BEGIN IMMEDIATE; ... COMMIT;")` in [src-tauri/src/db/schema/migrations/v8_to_v9.rs](../src-tauri/src/db/schema/migrations/v8_to_v9.rs:15) and [src-tauri/src/db/schema/migrations/v9_to_v10.rs](../src-tauri/src/db/schema/migrations/v9_to_v10.rs:15). If a statement fails after `BEGIN`, the code maps the error but does not explicitly roll back the long-lived connection. Both migrations also use `unwrap_or(...)` for reading `schema_version`, which can hide real schema-version read errors as a migratable old version.

Impact:

- A migration failure can leave the connection inside an open transaction, causing follow-up commands to fail in harder-to-diagnose ways.
- Corrupt or malformed `schema_version` state can be treated as a normal old schema rather than surfaced as database corruption.

Suggested fix:

Use a small migration helper that does:

- Read `schema_version` explicitly and only default on the specific "no row/table" legacy case if that is still intended.
- `BEGIN IMMEDIATE`.
- Run statements.
- `COMMIT`.
- On any error after `BEGIN`, best-effort `ROLLBACK` before returning the mapped error.

This can mirror the explicit transaction handling already used in [src-tauri/src/db/queries/entries.rs](../src-tauri/src/db/queries/entries.rs:220).

Tests to add:

- Force a v8 to v9 failure by creating `entry_metadata_encrypted` before the migration while version is still 8, then assert the migration returns an error and the connection can still begin a new transaction.
- Force a malformed `schema_version` read and assert the error is surfaced rather than silently defaulting.

### 8. Replace fixed-path auth test fixtures with temp directories

Severity: Medium

The known backend auth failures are consistent with fixed relative test database paths under `src-tauri/` and stale artifacts from previous runs. The failed paths include files like `test_auth_cmd_change_pw_v3.db` and `test_auth_cmd_reg_pw_unlock.db`. Even when not caused by product code, this blocks reliable validation and makes unrelated branch reviews noisy.

Suggested fix:

Update auth test helpers such as `make_state(...)` to allocate a `tempfile::TempDir` per test and return a guard that lives until cleanup. Avoid shared fixed filenames for DBs, backups, key files, and moved-journal directories. Where fixed paths are unavoidable, remove any pre-existing file/directory before creating the test DB.

Tests to add:

- No new functional test is needed; the fix is proven by running the auth module and full backend suite repeatedly without stale-artifact failures.

## Review Verdict

Not merge-ready yet. The branch is directionally solid, but it needs fixes for the lint blocker, the stored-link opener boundary, and the import/image-store round-trip gap before it meets the project's privacy-first and maintainability bar. The image picker scaling and migration rollback items should also be addressed before release, because they are cheaper to fix now than after users accumulate image-heavy journals.
